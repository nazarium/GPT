# Резервні копії Cloudflare → Google Drive

## Налаштування

Використати наявний Google Cloud проєкт або назвати новий Archi-Create Backups.
Увімкнути Google Drive API. Створити OAuth client типу Web application.
Додати дозволений redirect URI https://archi-create.com.ua/api/backup/google/callback.
Для фонового доступу потрібен OAuth consent screen у режимі Production.
У зовнішнього застосунку в режимі Testing refresh token може завершуватися через 7 днів.
Scope застосунку https://www.googleapis.com/auth/drive.file.

Секрети Worker вводяться через захищене поле Cloudflare або wrangler secret put.

- BACKUP_SIGNING_KEY — незалежний випадковий ключ. Зберегти окрему захищену копію поза Google Drive.
- GOOGLE_BACKUP_CLIENT_ID та GOOGLE_BACKUP_CLIENT_SECRET — створений OAuth client.
- CLOUDFLARE_BACKUP_API_TOKEN — токен відповідного акаунту з правом Account → D1 → Edit. Штатний експорт потребує Edit, оскільки тимчасово блокує D1. Перевірити дозволи тестовим експортом.
- LEGACY_BACKUP_SIGNING_KEY — за потреби старий пароль, яким підписувалися попередні JSON. Без цього секрету старі файли перевіряються поточним ADMIN_PASSWORD. Перед зміною пароля зберегти старий ключ у цьому секреті.

Публічні ідентифікатори BACKUP_ACCOUNT_ID, BACKUP_D1_ID задані у wrangler.jsonc.
Refresh token зберігається зашифровано в окремому Durable Object DriveBackup.
Він не потрапляє в content.json.

Після налаштування секретів опублікувати Worker, у вкладці резервних копій натиснути
«Підключити Google Drive», підтвердити Google, виконати «Створити повну копію зараз».
Увімкнути розклад після перевірки першої завершеної копії.

## Склад і гарантії

Кожна копія — окрема приватна папка. content.json містить KV-контент і завантажені
фото. social.sql — штатний SQL-експорт D1 зі схемою та даними, включно зі службовими
налаштуваннями соцмереж. Статичні файли з dist зберігаються окремими файлами.
manifest.json містить відносні шляхи, Drive IDs, розміри, SHA-256, коміт GitHub,
ознаку незакомічених змін і підпис HMAC-SHA256.

Папка має позначку «незавершена», доки всі файли не перевірені.
Передача виконується блоками по 4 МіБ з перевіркою підтвердженої позиції.
Зміна контенту під час його експорту скасовує файл. Зміна збірки під час роботи
скасовує завдання. Кожне сховище знімається окремо, час початку й завершення
вказаний у manifest. Спільного атомарного знімка Durable Object та D1 немає.
Штатний експорт D1 тимчасово блокує запити до цієї бази.
Невдала копія відображається в адмінпанелі, попередні завершені копії зберігаються.

Копії старше 365 днів переміщуються у кошик Drive після нового успішного запуску.
Це стосується лише папок, створених застосунком і позначених як завершені.
Потрібне вільне місце у Google Drive й відповідні ліміти Cloudflare.
R2 не використовується.

## Відновлення

1. Завантажити всю папку завершеної копії з Google Drive, розпакувати її.
2. Задати BACKUP_SIGNING_KEY у середовищі локального процесу.
3. Виконати node scripts/verify-full-backup.mjs <папка>. Скрипт перевірить підпис,
   розміри й SHA-256 всіх файлів та підготує підпапку restored.
4. Використати коміт із manifest для коду Worker. Якщо workingTreeDirty=true,
   потрібна також робоча копія коду відповідної збірки.
5. Відновити content.json через існуючий імпорт адмінпанелі з тим самим
   BACKUP_SIGNING_KEY на цільовому Worker.
6. Файли restored/static скопіювати до dist для розгортання статичних ресурсів.
7. social.sql імпортувати в окрему нову D1 через Wrangler і перевірити таблиці,
   потім перемкнути SOCIAL_DB. Перед відновленням призупинити автоматизацію
   соцмереж, щоб старі черги не створили повторні публікації.
8. Налаштувати секрети, домен і bindings окремо. Повторно підключити Google Drive.

Повна папка має інший формат, ніж ручний JSON. Імпорт JSON відновлює лише
content.json. D1, статичні файли й розгортання коду відновлюються кроками вище.
Секрети Worker та DNS не включені до папки.
